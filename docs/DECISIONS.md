# Решения, промпты, ограничения

## 1. Главная идея

Задание проверяет одно главное свойство: **модель не должна выдумывать характеристики**.
Полагаться только на промпт для этого нельзя, поэтому ответственность разделена:

| Часть карточки | Кто делает | Почему |
|---|---|---|
| Список характеристик | **код**, дословно из входа | Модели нечего исказить — она его не пишет |
| «данных нет» для отсутствующего | **код**, по профилю типа прибора | Детерминированно и проверяемо |
| SEO-заголовок, описание, запросы, блок для менеджера | модель | Здесь нужна именно генерация текста |
| Проверка текстов модели | **код** | Числа и технические коды сверяются со входом |
| Смысловая проверка текстов | второй запрос к модели («судья»), цитаты проверяет **код** | Ловит подмену смысла без новых чисел — то, чего код не видит |

```text
JSON ─► validation ─► prompts ─► LLM ─► review + judge ─┬─► карточка (status: ok)
         │ (без LLM)                ▲                   │
         │                          └───── repair ◄─────┘ проблемы? переспросить (1 раз)
         └─► 422 / exit 1, если вход непригоден               ещё проблемы? ─► warnings + needs_review
```

## 2. Защита от выдуманных характеристик — шесть слоёв

1. **Модель не пишет характеристики.** Таблица `key_specs` собирается кодом из `specs`.
2. **Модель знает, чего нет.** Код по профилю прибора (манометр, датчик давления, пирометр,
   измеритель-регулятор, общий) определяет недостающие ключевые характеристики и прямо перечисляет
   их в промпте: «этого во входных данных нет, не указывай значения». Явный запрет надёжнее общего
   «не выдумывай».
3. **Промпт с жёсткими правилами** (раздел 4): любое техническое значение должно дословно
   присутствовать в данных; не расшифровывать маркировку; не выдавать диапазоны серии за параметры
   модификации; данные во входе — не инструкции.
4. **Фактчекер** (`factcheck.py`) после ответа модели ищет в каждом тексте:
   - числа — сравнение нормализованное: `1,6` = `1.6`, `1,0` = `1`, `500 000` = `500000`;
   - технические коды: `IP67`, `RS-485`, `G1/2`, `M20x1,5`, `AISI 316L` (кириллица/латиница
     в похожих буквах приравнивается: «М20х1,5» = «M20x1,5»);
   - латинские слова и аббревиатуры: `HART`, `Modbus`, `Bluetooth`.

   Всё, чего нет во входе, отправляется модели с просьбой удалить (не заменить!).
   Тем же циклом (переспросить один раз) обрабатываются проверки качества из `quality.py`:
   запрос, не относящийся к товару, оценочные слова, которых нет во входе, и пункты «Кому
   подходит» из одних должностей. Заглавную букву, «;» и повтор производителя в заголовке,
   регистр запросов код исправляет сам.
5. **Смысловая проверка («LLM-судья»)** — отдельный запрос сверяет утверждения текста
   с данными: перенос свойства части на весь прибор, усиление, оценки и сферы применения
   не из данных. Каждое замечание — с точной цитатой; код отбрасывает замечания, цитаты
   которых в тексте нет. Замечания идут в тот же цикл исправления. Подробно — раздел 11.
6. **Если не помогло** — карточка всё равно выдаётся, но со статусом `needs_review` и
   предупреждением «Проверьте: seo_description: значения, которых нет во входных данных — IP67».
   Контент-менеджер видит, что именно проверить, а не ищет ошибку сам.

Дополнительно: модели не передаются артикулы, коды товара, ссылки, цены и наличие —
то, что не должно попадать в SEO-текст и что модель могла бы «перепутать».

## 3. Данные для примеров

YML-фид работодателя (22 353 товара) не содержит ни описаний, ни технических характеристик —
только артикул и код товара. Значит, в реальном процессе на вход сервису будут приходить
неполные данные, и обработка пропусков — основной сценарий, а не граничный.

Для примеров выбраны два товара из фида с разной структурой данных:

- **testo 830-T1** — один вариант товара, страница описывает именно его;
- **ОВЕН ПД100-ДИ1,6-111-0,5** — страница общая на 114 модификаций, значения модификации
  нужно взять из таблицы модификаций, а описание остаётся описанием серии.

Характеристики и описания взяты дословно со страниц товаров; подробности и найденные ошибки
сайта — в [examples/README.md](../examples/README.md).

## 4. Промпты

Полный текст — в [`kip_card/prompts.py`](../kip_card/prompts.py). Ключевые решения:

**Системный промпт**

- *Роль и аудитория.* Контент-менеджер и SEO-редактор B2B-магазина КИПиА, аудитория —
  профессиональная, подбирает прибор под задачу. Это задаёт деловой тон без маркетинговой воды.
  Должности в промпте не перечисляются: в версии 1 модель копировала список покупателей
  в «Кому подходит», в версии 2 — фразу «специалист или снабженец» (раздел 10).
- *Никаких конкретных товаров в инструкциях.* Только шаблоны вида `<модель>`, `<тип прибора>`.
  В версии 1 пример запроса «пирометр с лазерным целеуказателем» попал в карточку датчика
  давления. Тест `test_system_prompt_has_no_concrete_products` следит, чтобы это не вернулось.
- *Правило фактов первым и отдельным блоком.* Перечислено, что считается техническим значением
  (число, единица, класс точности, сигнал, резьба, IP, материал, стандарт, Госреестр, страна,
  гарантия), — модели проще соблюдать конкретный список, чем абстрактное «не выдумывай».
- *Единицы как во входе.* «1,6 МПа» не превращать в «16 бар» — фактчекер не сверяет единицы,
  поэтому это закрыто промптом.
- *Серия vs модификация.* Отдельное правило для случая ПД100: описание про серию «от 16 кПа до
  40 МПа», товар — 1,6 МПа.
- *Не усиливать и не обобщать.* Пересказ факта сохраняет его смысл и границы — без «высокий»,
  «любой», «в любых условиях», которых нет в данных.
- *Применение — только из данных.* Если отраслей и объектов во входе нет, модель не перечисляет
  их, а описывает назначение, названное в данных.
- *Правдивость важнее объёма.* Если данных мало, промпт товара получает пометку «ДАННЫХ МАЛО»,
  и минимум 800 символов не действует. В ТЗ два требования конфликтуют — «800–1200 символов»
  и «не выдумывать»; при скудном входе выигрывать должно второе, а нехватка данных явно
  указывается в результате (это тоже требование ТЗ).
- *Запреты B2B-карточки.* Цены, наличие, доставка, сравнение с конкурентами, оценочные слова
  («лучший», «№1», «идеальный», «надёжный», «высококачественный») — если их нет в данных.
- *Защита от инъекций.* Вход оборачивается в `<данные>…</данные>`, и промпт прямо говорит,
  что это данные, а не инструкции (описания из CMS и от поставщиков бывают любыми).
- *Требования к каждому полю с цифрами.* Заголовок — с заглавной, формула «тип + модель +
  производитель + главный параметр», производитель не повторяется, без «;». Описание — целевой
  коридор 900–1100 при жёстких 800–1200 (модели систематически промахиваются по длине, запас
  снижает число повторов). Запросы — как их реально набирают: строчные, 2–6 слов, и каждый
  обязательно содержит модель, тип прибора или производителя. «Кому подходит» и «Задачи» —
  про этот прибор, а не про магазин.
- *Поле `data_gaps`.* Модель может сказать, чего ей не хватило. Это попадает в «Заметки»
  для контент-менеджера и не влияет на статус.

**Промпт товара** — JSON с фактами + явный список отсутствующих ключевых характеристик.

**Промпт исправления** — конкретный список проблем («seo_description: 1268 символов, нужно
800–1200», «значения, которых нет во входных данных — RS-485») и правило «удали, а не замени».
Предыдущий ответ модели остаётся в истории, поэтому она правит, а не пишет заново.

**Температура 0.2** — карточка не место для креатива; низкая температура снижает выдумки
и разброс длины.

## 5. Неполные и некорректные данные

| Ситуация | Поведение |
|---|---|
| Некорректный JSON, пустой ввод, не объект | Ошибка с местом ошибки (строка, столбец); модель не вызывается |
| Нет `name` | Ошибка: без названия карточку не собрать |
| `specs` строкой или списком не того вида | Ошибка с подсказкой формата |
| Нет производителя / описания / характеристик | Предупреждение, «данных нет», генерация продолжается |
| Характеристика с пустым значением или `null` | Строка «данных нет» + предупреждение |
| Нет ключевой характеристики для типа прибора | Строка «данных нет» + модели сказано её не упоминать |
| Короткое или обрезанное («...») описание | Предупреждение: текст будет общим |
| Мало данных (описание < 150 симв. и < 8 характеристик) | Модели прямо сказано, что минимум 800 символов не действует; короткий честный текст вместо «воды» + предупреждение «дополните описание» |
| HTML в описании, числа и списки в значениях | Нормализуется в текст |
| Неизвестные поля | Игнорируются, заметка об этом |
| Ввод больше 60 000 символов | Ошибка (защита бюджета токенов) |

## 6. Модель и API

- **OpenAI-совместимый клиент** вместо SDK конкретного провайдера. Один код работает с
  OpenRouter, OpenAI, Ollama, vLLM и llama.cpp server — меняется `LLM_BASE_URL` в `.env`.
  Для компании с моделями в замкнутом контуре это значит: прототип переносится на свой сервер
  без изменения кода.
- **OpenRouter по умолчанию** — один ключ, любая модель, легко сравнить качество разных моделей
  на одних и тех же товарах.
- **Структурированный ответ по лестнице**: `json_schema` (строгая схема) → `json_object` →
  JSON по инструкции. Режим `auto` спускается по ней, если сервер не поддерживает более строгий
  вариант, и запоминает рабочий. Для OpenRouter добавляется `provider.require_parameters`, чтобы
  запрос шёл только к провайдерам, которые реально поддерживают схему. Рассуждающие модели
  (`gpt-5.x` и др.) часто не принимают `temperature`, и из-за этого OpenRouter отклоняет
  и схему — поэтому перед спуском клиент один раз повторяет строгую схему без `temperature`
  (так было в прогоне `gpt-5.4-mini`: схема не включилась, раздел 12).
- **Ошибки API переводятся в понятные сообщения**: неверный ключ, нет средств (402), лимит (429),
  таймаут, сервер недоступен, модель не найдена. Сетевые сбои и 429/5xx повторяет сам SDK
  (2 повтора с паузой).

## 7. Почему без LangChain

Здесь два вызова модели (генерация и смысловая проверка) с детерминированными проверками
вокруг и одним циклом исправления. LangChain добавил бы слой абстракций и зависимостей,
не дав ничего, что нельзя прочитать в `generator.py`, `judge.py` и `llm.py` (вместе около
600 строк). Он (или LangGraph) оправдан, когда появятся агент с инструментами, несколько шагов
с ветвлениями или RAG с несколькими источниками — см. улучшения.

## 8. Ограничения

- **Единицы измерения не сверяются.** «1,6 бар» вместо «1,6 МПа» фактчекер пропустит
  (число 1,6 есть во входе). Закрыто только промптом.
- **Смысловые искажения без чисел и кодов** («взрывозащищённый», «для агрессивных сред»)
  фактчекер не видит. Реальные примеры: «под высоким напряжением» вместо «под электрическим»,
  «корпус из AISI 316L» вместо «мембрана из AISI 316L». Их ловит модель-судья, но **судья —
  тоже модель**: он может пропустить искажение или придраться к допустимому пересказу.
  Проверка цитат защищает только от замечаний «из воздуха», а не от пропусков. Поэтому
  результат сервиса — черновик для вычитки, а не готовая карточка.
- **Смысловая проверка удваивает число запросов** и время ответа (около 2–4 запросов на
  карточку вместо 1–2). Выключается `JUDGE=off`.
- **Шаблонность «Кому подходит»** контролируется промптом и частично кодом (должности,
  числа в пунктах): код не может судить, подходит ли пункт конкретному прибору.
- **Сравнение моделей — по одному прогону на товар** (раздел 12): ответы моделей от раза
  к разу различаются, поэтому это тенденция, а не измерение. Для выбора модели в работе
  нужен эталонный набор товаров и метрики (улучшение 6).
- **Судья на той же модели, что генератор** (если на сервере помещается одна модель) — слабее:
  ошибки генератора и судьи связаны.
- **Скорость Qwen через OpenRouter нестабильна:** от 16 секунд до нескольких минут на карточку
  (рассуждение перед ответом, мало провайдеров со строгой схемой, до четырёх запросов на карточку).
  В замкнутом контуре скорость определяет своё железо; для пакетной обработки каталога нужна
  очередь и параллельные запросы (улучшение 7).
- **Сокращения и повторы ловятся по шаблонам:** «изм. знач.», два предложения из одних и тех же
  слов. Перефразированный повтор другими словами код не увидит — его ловит только судья.
- **Повторы проверяются внутри одного текста.** Сводка для менеджера может повторять фразы
  SEO-описания, а пункт «Какие задачи решает» — пересказывать назначение прибора с диапазоном
  (манометр в итоговом прогоне). Код этого не видит, судья такие пункты не считает ошибкой.
- **Числа во входе разрешены везде.** Если число есть где-то во входе, модель может приписать его
  не той характеристике — проверка этого не заметит.
- **Длина текста контролируется повтором, а не гарантируется.** После одной попытки исправления
  карточка выдаётся с предупреждением.
- **Профили приборов — пять штук** с ручными наборами ключевых характеристик; остальные типы
  проверяются по общему набору из ТЗ.
- **Нет пакетной обработки каталога** и кеша: каждый вызов — новый запрос к модели.
- **Входные данные для примеров собраны вручную** со страниц сайта: фид характеристик не содержит.
- **Ошибки в исходных данных не обнаруживаются** — сервис доверяет входу.

## 9. Возможные улучшения

С прицелом на задачи компании (каталог на 1С-Битрикс, свои серверы, документация к приборам):

1. **RAG по паспортам и руководствам.** На страницах товаров уже лежат PDF («Описание типа СИ»,
   «Руководство по эксплуатации»). Индекс по ним позволит дозаполнять «данных нет» со ссылкой на
   страницу документа, а контент-менеджер будет подтверждать, а не искать.
2. **Интеграция с Битриксом.** Брать свойства инфоблока напрямую (REST API или выгрузка), а не
   через YML; возвращать черновик в отдельные свойства на модерацию.
3. **Проверка согласованности входа до генерации.** Ловить ошибки вроде найденных на странице
   ПД100: характеристика не соответствует названию, модификация противоречит соседним.
4. ~~Второй проход «LLM-судья»~~ — **сделано** (раздел 11). Дальше: метрики судьи на эталонном
   наборе (сколько искажений ловит, сколько ложных замечаний), сравнение моделей для судьи.
5. **Сверка единиц измерения** — парсинг «число + единица» и сравнение пар, а не только чисел.
6. **Набор эталонных товаров и метрики**: доля карточек без замечаний, число повторов,
   длины, доля «выдумок» по фактчекеру — для выбора модели и регрессии при смене промпта.
7. **Пакетная обработка** каталога с очередью, кешем по хешу входа и отчётом для контент-менеджера.
8. **Локальная модель в контуре компании** (vLLM + Qwen2.5 / аналог) — код уже готов, нужно
   выбрать модель по метрикам из п. 6.

## 10. Первый прогон на реальной модели: что нашёл и что исправил

Первый прогон — `openai/gpt-4o-mini` через OpenRouter, промпт версии 1, три товара из
`examples/input`. Фактическая часть отработала: ни одного выдуманного числа или кода,
все три ответа прошли фактчекер с первой попытки, строгая JSON-схема поддержана.
Ручная вычитка нашла проблемы качества:

| Что нашёл | Причина | Что сделал |
|---|---|---|
| В карточке датчика давления запрос «пирометр с лазерным целеуказателем» | Модель скопировала пример запроса из системного промпта | Из промпта убраны все конкретные товары — только шаблоны `<модель>`; код проверяет, что в каждом запросе есть слово из названия, типа, категории или производителя; тест на отсутствие конкретики в промпте |
| «Кому подходит» одинаковый у всех трёх приборов | В промпте был перечень покупателей магазина, модель его переписала | Перечень убран; требование «кто и где применяет именно этот прибор, у разных приборов пункты различаются» |
| У манометра «химическая и пищевая промышленность», «резервуары», «лаборатории» — в данных этого нет | Правило про применение было мягким | Явное правило: отрасли и объекты — только из данных, иначе описывать назначение |

смысловые искажения, которые детерминированные проверки не видят.

## 11. Смысловая проверка: модель-судья

**Зачем.** После трёх итераций промпта остались только смысловые искажения: «корпус датчика
выполнен из AISI 316L» при «мембрана из AISI 316L» в данных, «достаточная точность для
большинства задач». Первое — по сути выдуманная характеристика (материал корпуса), то есть
нарушение главного требования ТЗ, но без единого нового числа или кода. Детерминированные
проверки такое не видят в принципе (тест `test_third_run_pd100_passes_deterministic_checks_but_not_judge`
показывает это на настоящем ответе модели). Дальнейшее ужесточение промпта даёт убывающую отдачу:
ответы модели от прогона к прогону разные, и одно и то же искажение то исчезает, то возвращается.

**Как устроено** (`kip_card/judge.py`):

1. После каждой генерации — второй запрос: системный промпт фактчекера, входные данные
   в `<данные>`, тексты карточки в `<тексты>`. Ответ — строгая JSON-схема:
   `{"issues": [{"field", "quote", "data_evidence", "verdict", "reason"}]}`. Судья обязан
   приложить к замечанию дословный фрагмент данных о том же предмете (`data_evidence`, пусто —
   «в данных об этом нет») и вердикт: `not_in_data`, `contradicts`, `amplified`, `evaluation`
   или `confirmed`. Поиск фрагмента заставляет действительно свериться с данными, а не судить
   по памяти о прочитанном.
2. **Код проверяет цитаты.** Замечание принимается, только если `quote` дословно (без учёта
   регистра, пробелов, вида тире и кавычек) есть в указанном поле. Иначе — отбрасывается:
   судья не может «придумать» проблему, которой в тексте нет. Отбрасываются и замечания
   с вердиктом `confirmed` и с цитатой, дословно взятой из данных. Фрагмент данных, которого
   в данных нет, не показывается; настоящий — показывается в предупреждении:
   «Проверьте смысл: «…» — причина (в данных: «…»)», чтобы человек сразу видел, на что
   опирался судья.
3. Принятые замечания добавляются к проблемам детерминированных проверок и уходят генератору
   **одним** промптом исправления. Исправленный текст проверяется снова — и кодом, и судьёй.
4. Что осталось — предупреждение «Проверьте смысл: «цитата» — причина», статус `needs_review`.
5. **Сбой судьи не ломает карточку**: она выдаётся с предупреждением «смысловая проверка
   не выполнена» и статусом `needs_review`. Генерация важнее проверки, но человек должен знать,
   что гарантии нет.
6. Результат — в `meta.judge_status` (`off`, `passed`, `issues`, `error`) и `meta.judge_model`.

**Решения:**

- *Судья не переписывает текст.* Он только указывает на проблему. Править — задача генератора,
  у которого есть весь контекст и правила формата. Так у судьи одна простая задача,
  и его ошибка не может испортить текст напрямую.
- *Отдельная модель для судьи* (`JUDGE_MODEL`), **другого семейства, чем генератор.**
  Если генерирует и проверяет одна модель, их ошибки связаны: что модель неверно поняла
  при генерации, она так же поймёт и при проверке; в исследованиях LLM-as-judge описана
  и склонность моделей оценивать свои ответы выше чужих (self-preference). Проверка ценна,
  когда ошибается независимо. Рекомендуемая пара — раздел 12. Если `JUDGE_MODEL` пуст,
  судья — та же модель (вариант для сервера, где помещается одна модель). Температура судьи — 0.
- *Тот же OpenAI-совместимый клиент и та же лестница режимов JSON* — судья работает и с
  локальной моделью в замкнутом контуре.
- *В промпте судьи нет конкретных товаров* — по опыту первого прогона (тест следит).
- *Стоимость.* С `gpt-4o-mini` — доли цента на карточку. Для пакетной обработки каталога
  судью можно включать выборочно или запускать на дешёвой модели.

## 12. Выбор моделей: сравнение на одних товарах

Три модели на тех же трёх товарах, промпт версии 3, судья — та же модель, что генератор.
По одному прогону на товар, поэтому это тенденция, а не измерение (раздел 8).

| | `openai/gpt-4o-mini` | `openai/gpt-5.4-mini` | `qwen/qwen3.8-27b` |
|---|---|---|---|

**Выбор по умолчанию** (`.env.example`):

### Прогон версии 5 и доказательства судьи

Прогон: Qwen + судья `gpt-5.4-mini`, промпт версии 5. По договорённым критериям
(нет выдуманных фактов, нет ложных пометок, ПД100 и testo — `ok`, у манометра — без тавтологий):

- **Манометр** — соответствует: 197 символов без «воды», «Кому подходит: данных нет»,
  запрос «dm 02» без ложной пометки, `needs_review` из-за неполных данных — как и должно быть.
- **testo** — `ok`: всё по данным, без сокращений и служебных оборотов.
- **ПД100** — текст без ошибок, но два ложных замечания судьи: (1) к заголовку, с выводом самого
  судьи «Остальное подтверждается»; (2) «канализация не названа прямо», хотя в данных есть

Обе ошибки судьи — одного типа: он не сверился с данными, хотя промпт это требует. Поэтому
вместо ещё одного правила в промпте судья теперь обязан приводить доказательство — дословный
фрагмент данных и вердикт (см. раздел 11). Случай (1) отбрасывается по вердикту `confirmed`;
в случае (2) поиск фрагмента должен найти фразу про канализацию, а если судья всё же ошибётся,
приложенная цитата покажет человеку ошибку сразу. Ответы прогона — `tests/fixtures/v5_run/`:
все три карточки проходят проверки кода без замечаний.

### Итоговый прогон

ПД100 и testo — `ok` с первой и второй попытки, ложных замечаний судьи нет: доказательства
сработали. В манометре — повтор: «Присоединение G1/2, диаметр корпуса 100 мм» и сразу
то же самое в следующем предложении. Проверка повторов его пропустила: она сравнивала только
предложения не короче четырёх значимых слов, а в первом их три. Добавлено правило для коротких
фраз: повтор, если все значимые слова (от трёх) есть в другом предложении. На всех сохранённых
ответах моделей проверка находит ровно четыре известных повтора и ни одного ложного
(`test_repeat_check_finds_exactly_known_repeats_across_all_runs`). Манометр перегенерирован
с этой проверкой: одна попытка, судья `passed`, повтора нет, «Кому подходит: данных нет»,
221 символ, `needs_review` только из-за неполных данных.
Все три карточки соответствуют договорённым критериям; на этом итерации промпта завершены.
Оставшиеся мелочи — повтор фраз между сводкой для менеджера и SEO-описанием, пункт задач,
повторяющий назначение с диапазоном, — описаны в ограничениях (раздел 8) и в
[examples/README.md](../examples/README.md).
